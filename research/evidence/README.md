# RoadImpact 0.4 — evidence-first QA pilot (read-only)

This is an independently runnable, zero-dependency subset of the full RoadImpact 0.4 release. It lives on an isolated **research branch** of a private GitHub repository. It does **not** update OpenStreetMap, automatically open issues/challenges, or assert that humanitarian responders use these outputs.

## What changed after the Bunia imagery investigation

Two genuine OSM topological gaps were rechecked on 2026-10-15. In both cases the best accessible satellite imagery was **captured 2025-06-14**, before the current OSM road edits, and the imagery had a reported **0.34 m resolution but 5 m absolute positional accuracy**. Zoom 19–20 returned low-variation placeholder tiles and were rejected; zoom 18 was the highest useful source. We cannot prove a vehicle connection from these data. **Case A is a human-review candidate, B is deferred because of vegetation.**

The triage does not output road geometry to upload, and never marks a candidate edit-ready.

## Run without dependencies

From the repository root:

```bash
python -m unittest discover -s research/roadimpact-evidence-v04 -p 'test_*.py' -v

python research/roadimpact-evidence-v04/triage.py \
  --input research/roadimpact-evidence-v04/bunia-cases.json \
  --output research/roadimpact-evidence-v04/output/triage.json \
  --as-of 2026-10-15T21:30:00+02:00

python research/roadimpact-evidence-v04/benchmark.py \
  --input research/roadimpact-evidence-v04/output/triage.json \
  --output research/roadimpact-evidence-v04/output/benchmark.json
```

CI runs these commands on each change to this directory. See [.github/workflows/roadimpact-evidence-benchmark.yml](../../.github/workflows/roadimpact-evidence-benchmark.yml).

**Expected CI:** 1 human-review case, 1 deferred case, 0 confirmations, **precision = null**, 2 unlabeled real cases and **198 as-yet-unfilled review slots**.

## What constitutes a credible 200-case benchmark

The target is **200 independently sampled and reviewed cases**, not 200 suspicious coordinates generated by a model. The current 2-case dataset is **not** a statistically valid benchmark.

1. Agree in advance with experienced HOT/OSM mappers on areas, data protection and which OSM-licensed imagery is appropriate.
2. Sample both detector-selected hypotheses and baseline/control locations; include known cul-de-sacs, grade-separated crossings and ambiguous images. Use diverse road types, areas, and sampling methods to reduce bias.
3. Two blinded qualified reviewers independently decide whether *each transport mode* has a verified connection, record source provenance and minutes spent. Have an independent third reviewer adjudicate disagreements.
4. Mark a **real accepted correction** only after its OSM changeset is accepted. No label can be inferred from OSM geometry or satellite pixels alone.
5. Evaluate evidence ranking and distance-only baseline **on the same sampled population**, with unknowns visible. Report precision@20 only when all top-k cases are adjudicated; report unresolved rate, false vehicle connections, and accepted corrections/hour. A causal productivity claim additionally needs a controlled reviewer trial.
6. Do not publish sensitive sites or run large-scale downloads from the OSM edit API. For country-scale research, use approved regional extracts rather than hammering community APIs.

No synthetic ground-truth examples are present in this **GitHub CI** dataset. The full Python package has a separate, explicitly synthetic harness solely for software regression testing.

## What the score means

The numeric score is an **explainable review heuristic**, not a calibrated probability. It rewards current topology and possibly visible passages, penalizes stale imagery, unregistered offsets, inaccessible image tiles and vegetation occlusion. It does *not* authorize OSM changes. Even image-level visual continuity cannot prove legal access or vehicle passability.

The output files contain metadata, not copyrighted satellite imagery. OSM-derived data remain © OpenStreetMap contributors (ODbL). OSM's [good practice](https://wiki.openstreetmap.org/wiki/Good_practice) requires checking imagery alignment and currency. The [automated edits policy](https://wiki.openstreetmap.org/wiki/Automated_edits) requires community coordination for systematic editing.
